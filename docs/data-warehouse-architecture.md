# 小象避坑数据仓库设计（第一阶段）

状态：待产品确认

## 1. 目标与范围

第一阶段面向中国普通 C 端用户，支持日本住宅、预售/新建项目和商业项目投资的资料提交、数据补全、市场对比和风险分析。输入包括自然语言、房产链接、PDF 和图片；输出为可追溯的项目评估报告。

本阶段不做无授权的全网爬取，不把 AI 估算当作事实，也不向用户承诺收益或替代持牌专业意见。

## 2. 数据分层

```text
数据源登记
  → 原始快照
  → 标准化实体
  → 指标与风险结果
  → 用户报告与脱敏统计
```

### 2.1 数据源登记层

记录来源名称、URL、来源类型、采集方式、授权状态、更新频率、解析器版本、最近成功和失败时间。每个来源必须有负责人和使用限制。

### 2.2 原始快照层

每次采集保存抓取时间、请求 URL、内容哈希、原始内容、HTTP 状态和解析器版本。历史快照不可被新数据覆盖，以支持审计、回放和重新解析。

### 2.3 标准化层

核心实体包括：

- `properties`：项目身份、区域、建筑和权利信息
- `residential_details`：住宅专属字段
- `new_build_details`：预售/新建项目专属字段
- `commercial_investment_details`：租赁合同、租客和经营专属字段
- `evidences`：原始文件、链接、页码、字段出处和提取方式
- `sources`：数据来源和授权信息
- `users` / `workspaces`：用户与私有项目空间

字段需要同时保存数值、单位、币种、观察时间、数据分类和可信度。数据分类至少包括 `verified_observation`、`scraped_aggregate`、`modeled_estimate`、`synthetic_fixture` 和 `user_submitted`。

### 2.4 指标与风险层

收益率、现金流、空置调整、区域排名和风险评分独立保存，不覆盖原始字段。每个结果记录 `calculation_version`、假设集和计算时间，便于模型升级后重算和追溯。

## 3. 采集与更新

采集任务通过队列和调度器执行，具备限速、超时、重试、去重、内容哈希、失败告警和数据质量检查。

- 快速变化数据：每日或用户触发更新
- 区域和租金统计：每周更新
- 人口、交易、灾害和宏观数据：每月或季度更新
- 用户链接、PDF、图片：提交后即时解析，并保留原始文件

只采集有明确权限或公开授权的数据。对于商业房源网站，先确认使用条款、robots 规则、访问频率和展示权限；必要时使用授权接口、人工录入或用户主动提交替代自动抓取。

## 4. 用户隐私和数据权限

用户原始资料进入私有项目空间，默认只有用户本人、被授权的客服/分析师和必要的 AI 服务可访问。每条记录必须由后端登录身份绑定 `owner_user_id` 和 `workspace_id`，不能用前端传入的邮箱判断归属。

客户消费分析只使用脱敏、聚合后的特征，例如区域、预算区间、项目类型、关注风险和操作结果。公共页面不得展示用户原始文件、具体项目查询或可反推出用户身份的信息。管理员访问原始资料必须授权并写入审计日志。

数据用途明确区分：

- `private_analysis`：仅用于用户自己的分析
- `internal_product_analytics`：用于产品和客户需求统计
- `public_market_dataset`：审核后可公开的市场数据

## 5. 可扩展性规则

高频过滤和排序字段使用关系型列；来源差异大的附加字段使用 JSONB；文件和证据独立存储；指标、风险和报告独立建表。住宅、预售/新建项目和商业项目投资共享项目主表，但使用各自的详情表和风险规则。

增加普通字段应只涉及迁移、解析器和数据字典，不修改历史数据含义。涉及项目身份、区域层级、单位口径、权限边界或指标定义的变更，必须建立迁移方案并提升版本号。

## 6. 第一阶段实施顺序

1. 固化数据分类、来源和证据规范
2. 统一当前两个冲突的数据库 schema
3. 建立来源登记、原始快照和标准化项目表
4. 为住宅、预售/新建项目与商业项目投资建立最小指标和风险模型
5. 建立定时任务、失败告警和质量检查
6. 接入用户链接、PDF、图片解析
7. 生成可追溯的评估报告和脱敏消费统计

## 7. 暂不实施的事项

- 未确认授权前的大规模商业网站抓取
- 直接公开用户上传资料
- 将 AI 推测值写入已验证数据
- 用单一综合分数替代证据和风险明细
- 在没有历史样本和计算口径的情况下发布趋势结论

## 8. 待确认决策

上线前仍需确认：数据来源授权清单、原始文件保存期限、用户删除和撤回机制、消费分析授权文案，以及报告中住宅和商业项目投资的具体评分阈值。

## 9. 商业化方向（第一阶段）

### 9.1 C 端：单项目付费

C 端采用“免费预览 + 单项目分析报告”模式，不把月度订阅作为主要门槛。免费部分用于建立信任，包括项目基本信息、数据来源、更新时间、资料完整度和简单市场区间；付费部分包括 AI 综合分析、同类项目比较、现金流测算、住宅、预售/新建项目或商业项目投资风险清单、避坑指南、资料补充清单和可下载报告。

可选的附加服务包括人工专家复核、报告更新和多项目比较。支付成功后固定生成一个项目分析权益，权益应绑定项目版本和报告版本，避免重复扣费或报告内容不一致。

### 9.2 B 端：数据服务和项目分析

B 端免费查询基础市场数据，收费提供客户需求分析、区域热度、项目匹配、批量比较、定制报告、团队协作和 API/数据导出。B 端产品的收费价值是帮助客户判断“什么项目适合什么需求”，而不是简单增加可见字段。

### 9.3 后期：需求撮合

C 端可发布结构化购房需求，B 端提交匹配项目。联系方式和个人资料默认隐藏，只有用户明确同意后才交换。平台需记录推荐、查看、联系和成交状态，并明确展示推广关系和利益冲突。

### 9.4 市场验证原则

社交平台上的搜索或内容热度可以作为需求信号，但不能直接等同于有效购房人数或可实现收入。上线后应持续记录注册、资料上传、免费预览、付费转化、报告下载、退款和后续咨询等漏斗数据，用真实行为验证市场规模和定价。

## 10. 预售/新建项目分析

预售/新建项目作为独立项目类型纳入数据仓库，不与已建住宅简单混用。核心字段包括：开发商、项目状态、开盘日期、销售期、预计竣工日期、交付日期、户型、期数、单价、首付和付款节点、管理费预估、修缮积立金预估、地块和建筑许可、开发商历史交付记录及取消/变更条款。

核心分析包括：

- 预售价格与周边已建项目、历史成交的比较
- 开发商和施工方履约风险
- 预计交付前后的价格、租金和现金流情景
- 首付、尾款、贷款审批和汇率压力
- 交付延期、户型或配置变更、取消条款风险
- 管理费和修缮积立金从预估到实际的变化风险
- 周边配套、人口、交通和灾害条件的兑现程度

预售项目必须记录项目状态和观察时间，因为“未开盘、销售中、已售罄、延期交付、已交付”会直接影响分析结论。销售热度只能作为市场信号，不能替代合同、许可、开发商记录和可验证的价格数据。

## 11. 法规与政策数据层

日本的税费、住宅贷款、租赁、建筑、民宿经营、外国人购房和区域限制等政策会影响项目分析结果，必须作为独立数据层维护。法规内容不能直接覆盖旧版本，而应保存版本和适用期间。

每条政策至少记录：

```text
policy_id
title
jurisdiction
authority
source_url
published_at
effective_from
effective_to
status
scope
summary
impact_categories
reviewed_by
reviewed_at
```

优先使用日本中央政府、都道府县、市区町村、金融机构和其他正式发布机构的原始来源。每个政策来源需要保存原文快照、发布日期、更新时间和解析版本，并设置失效检查和人工复核任务。

政策变化需要能够关联到受影响的分析模块，例如：

- 税费政策 → 购买成本和持有成本
- 贷款政策 → 融资额度、利率和现金流
- 建筑与区域规划 → 可建性、用途和改建风险
- 租赁与经营规则 → 租金、退租和运营风险
- 外国人相关规定 → 交易流程和资料要求
- 灾害与土地政策 → 区域风险和保险假设

政策更新后，系统应标记受影响的历史报告，提示需要重新计算或人工复核，而不是静默改变用户已经购买的报告结论。报告必须显示引用的政策名称、来源、有效日期和适用范围。

## 12. 宅建业法、民法与交易节点提示

法规知识库需要覆盖宅地建物取引業法、民法中与不动产买卖和租赁相关的规则，以及国土交通省发布的重要事项说明、IT 重要事项说明和书面电子化资料。日本国土交通省说明，买方或承租人在不动产交易中会接受宅地建物取引业者关于应知重要事项的说明；相关说明和书面交付要求应以当时有效的法律和官方解释为准。

系统在分析项目时，不替代宅地建物取引士、律师或税务师作出法律判断，而是生成“交易前检查提示”：

- 是否应要求提供重要事项说明书
- 重要事项说明的对象、时间和方式是否明确
- 说明人是否为适格的宅地建物取引士，并确认其证件和所属机构
- 土地权利、用途限制、接道、建筑限制和灾害信息是否已核对
- 买卖合同、租赁合同、定期借家合同和附带条款是否需要专业复核
- 预售项目的付款、竣工、交付、变更和解除条款是否清楚
- 商业项目投资的租客、租金、管理、保证和经营许可资料是否齐全

每条提示应关联具体证据、法规版本和有效日期，并标明“已核对、待补充、需专业人士确认”三种状态。若缺少重要事项说明书或关键合同，系统应降低资料完整度和结论置信度，而不是自动判定项目违法。

法律内容的展示必须有版本、来源和人工复核记录。报告页应明确：平台提供的是资料整理和风险识别，不构成法律、税务、金融或投资建议；签约前应向日本当地宅地建物取引士或律师确认具体交易。

## 13. 首期区域范围

总体规划覆盖以下市场：东京、大阪、京都、横滨、神户、北海道、名古屋和福冈。

数据模型必须区分：

```text
都道府县 / 都市圈
  → 市区町村
    → 行政区
      → 车站、街区和项目
```

其中北海道作为都道府县处理，不能直接当作单一城市；东京需要区分东京都、东京 23 区和多摩地区；横滨、神户、名古屋、福冈等城市还需要保留各自行政区层级。

建议分批上线：先选择数据来源最稳定、用户需求最明确的 2～3 个市场建立完整样板，再扩展到其余区域。即使首期只上线部分城市，数据库和来源登记表也应从一开始支持全部区域，避免后续重构区域模型。

## 14. 第一版报告固定章节

报告采用“固定主结构 + 项目类型专属分析”的方式，住宅、预售/新建项目和商业项目投资共用主结构。

固定章节包括：

1. 项目结论摘要：项目概况、收益区间、风险等级、资料完整度和三个最重要的问题
2. 项目基本信息：地址、面积、价格、租金、费用、建筑和权利信息
3. 数据来源与可信度：来源、更新时间、证据、样本数量、估算字段和置信度
4. 市场价格比较：同区域、同类型、同面积项目的价格区间和差异
5. 租金与收益分析：毛收益、净现金流、空置、融资、汇率和情景假设
6. 项目类型专项分析：住宅、预售/新建项目或商业项目投资的专属风险
7. 法律和重要事项检查清单
8. 深度避坑分析
9. 资料缺口清单
10. 下一步行动建议
11. 方法说明、版本信息和免责声明

### 14.1 法律和重要事项检查清单

该章节是资料核对和交易前提示，不替代宅地建物取引士、律师或税务师的专业判断。每项记录检查事项、适用法规或官方来源、当前状态、证据文件、潜在影响和下一步动作。

状态统一为：已确认、资料不足、存在异常、需要专业人士确认、不适用。检查范围包括重要事项说明书、宅地建物取引士说明、土地权利、用途和建筑限制、接道、灾害信息、合同条款、预售交付条款，以及商业项目投资的租赁和经营资料。

### 14.2 深度避坑分析

每项风险使用统一结构：风险名称、风险等级、发现依据、可能影响、所需补充资料、建议处理方式和是否触发暂缓推进。

风险类别包括价格、租金和收益、空置和租客、建筑和维修、合同、法规、开发商或管理公司、融资和汇率、数据可信度。

免费报告只显示资料完整度、基础风险摘要和待确认事项数量；付费报告提供完整证据、影响分析、情景测算、补充资料清单和行动建议。
