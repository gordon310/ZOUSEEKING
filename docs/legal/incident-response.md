# 隐私与安全事故响应流程

**状态：** 离线桌面演练流程；`privacy-2026-08`。本文件不会发送通知，也不包含真实个人资料。

## 1. 触发和分级

任何人发现 token 泄露、跨用户读取、私有文件公开、错误的删除、恶意批量请求、Auth 配置错误、第三方来源违规或备份异常，都应立即建立脱敏事件 ID。先保护人和数据，再判断是否构成适用法律下的个人数据事故。

| 级别 | 例子 | 初始动作目标 |
| --- | --- | --- |
| P0 | 已确认跨用户批量访问、refresh token/服务密钥泄露、私有 Storage 公开 | 立即升级负责人，**4 小时**内完成初步遏制/范围判断 |
| P1 | 单个用户资料越权、删除失败导致超期、Auth/RLS 错配 | **4 小时**内分派、遏制和保留证据 |
| P2 | 可恢复的单点故障、错误文案、无个人数据影响的配置问题 | 1 个工作日内修复或记录风险接受 |
| P3 | 低风险建议或近失事件 | 下个迭代纳入改进清单 |

## 2. 发现、遏制和证据

1. 只在受控渠道记录事件 ID、发现时间、系统组件、数据类别、初始影响和负责人；不复制原始请求、邮箱、姓名、令牌或附件。
2. **遏制：** 暂停受影响 token/账户/任务、收紧路由或 Storage 权限、停止不必要的 worker；不得直接在 production 执行未经批准的 SQL/RLS/Storage 删除。
3. 保留脱敏日志、配置版本、migration ID、访问审计、对象计数和时间线，设置只读权限与哈希；不要为了“清理痕迹”覆盖证据。
4. 确认是否有 staging/production 边界、第三方供应商或跨境影响；离线测试只使用 synthetic fixture。

## 3. 分析和通知决定

负责人、隐私负责人和法务根据事实判断受影响资料、数量、可识别性、风险、供应商义务和适用地区。形成书面的**通知决定**（通知/不通知、对象、依据、时间、批准人、待补证据），并记录法规时钟；不能用仓库测试结果代替事实调查。

本仓库任务默认**不发送通知**：没有真实收件人、运营主体、法务批准或在线事件。若将来需要通知，必须使用受控工单/邮件供应商、最小必要内容、反枚举模板和发送审计；不能把内部异常、token 或客户清单放入通知。

日本 APPI 相关判断应参考日本个人信息保护委员会的官方指引并由法务确认；PPC 的公开职责和泄露应对材料仅作为参考，不在本流程中替代法律意见。

## 4. 恢复和事后改进

修复前先准备回滚/forward-fix 和 backup/restore 方案；修复后分别验证 anonymous、owner、other authenticated user、service worker，核对 RLS、Auth、Storage、删除 SLA 和日志脱敏。恢复服务需由负责人批准，并向受影响用户说明仍存在的风险。

五个工作日内完成无责复盘：根因、检测延迟、遏制效果、受影响数据类别、通知决定、控制改进、测试补充和负责人/期限。不要把真实用户事件写进仓库 fixture；使用去标识化或合成案例。

## 5. 现阶段 blocker

- migration baseline 仍为 `reconciliation_required`，不能新增账户/同意/审计表；
- Supabase Auth Admin 删除、RLS/Storage 删除和持续清理 worker 尚未得到线上授权或演练；
- 运营主体、隐私负责人、客服邮箱、适用法和通知渠道未确认；
- 当前前端 localStorage 认证回退是既有 release blocker；
- 本流程未连接 staging/production、未读取真实事件、未发送通知。
